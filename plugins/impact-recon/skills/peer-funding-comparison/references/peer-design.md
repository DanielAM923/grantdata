# Peer design and financial comparability

Use when the user needs help choosing peers, including earned-revenue/business-model peers. Define the comparison's purpose before building a list: operating/financial analog, local funding-market reference, program analog or capital-stack neighbor. Keep those roles separate. Explain why each proposed organization belongs and let the user accept a set before using selected-peer funding tools.

Issue routes and native research can generate candidates when those capabilities are available; they do not automatically approve a comparable cohort. Verify mission/programs, operating role, service geography and scale on primary sources. Include developer/operators when a services-heavy list would distort the comparison. Do not select solely by funder density, NTEE or a similar name.

For earned-revenue peers, start with the user's desired revenue scale, charitable status, program-service/membership mix and business model. Distinguish training/credentials, association/standards, events/admissions, social-enterprise contracts, housing operations and technical services. Healthcare exclusions and revenue thresholds are user-specific screens, not universal defaults. The current selected-EIN financial tool cannot run a national revenue screen; use source-verified candidates or report the missing screen rather than inventing one.

Compare actual filing years and definitions. Separate recurring support from affiliate transfers, campaigns, noncash, restricted, exceptional and project receipts where the filings support it. A service organization and a housing developer may need separate benchmark bands. Ratios inform scale and questions, not first-year attainable cash or a hire recommendation. Apply the strategy's goal-calibration reference for targets.

Output the candidate/accepted peer set, role, source, metric/year and exclusion reason or remaining question. Label incomplete cohorts and tool caps; a returned top list is not the universe.
